# Bin Sticker Generator — Script Split Summary (Sep 2026)

Written for handoff/review (e.g. Cursor double-check), not as a standalone
project doc — cross-reference against the actual files before relying on
line numbers or exact figures below, in case anything drifts after this
was written.

## 1. Why this split happened

`bin_sticker.py` was one file (~3,300 lines) generating all sticker
designs at the single production size (140×100mm landscape, 25 styles).
We're now adding a second size (Medium, 210×140mm) and wanted the two
sizes' code to be structurally isolated — a bug or bad edit in one
size's style code should be unable to affect the other size at all, not
just "unlikely to."

The alternative (fully duplicating every shared helper into two
complete copies) was rejected: it would have meant every future fix to
shared logic (icon caching, font-fit, base/border drawing, sheet layout
math) needing to be applied twice, with a high chance the two copies
drift apart over time. Instead we extracted the genuinely shared,
size-agnostic code into one common module that both size scripts import.

## 2. Before → after

**Before:** one file, `bin_sticker.py`, ~3,300 lines, mixing:
- Size-agnostic plumbing (icon caching, accent palettes, base/border
  drawing, vector icon shapes, font-fit/curved-text helpers, sheet
  layout math)
- Size-specific content (25 styles' drawing functions and pixel-measured
  constants, all built for 140×100mm; the `STYLES`/`STYLE_LABELS`/
  `STYLE_PRODUCT_ID`/`STYLE_CARD_SIZE` registries)

**After:** three files.

| File | ~Lines | Contents |
|---|---|---|
| `bin_sticker_core.py` | 488 | Shared plumbing only. No styles, no registries, can't generate a sticker by itself. |
| `bin_sticker_small.py` | 2,907 | The original 25 styles at 140×100mm, importing shared code from core. |
| `bin_sticker_medium.py` | 399 | 3 pilot styles at 210×140mm, importing shared code from core. |

`bin_sticker_small.py` + `bin_sticker_core.py` together are the direct
replacement for the old `bin_sticker.py` — same behaviour, split across
two files. The old single-file `bin_sticker.py` is superseded and should
not be edited going forward; treat `small.py`/`core.py` as the current
source of truth for the 140×100mm product.

## 3. What moved into `bin_sticker_core.py`

Only code with zero card-size assumptions baked in:

- Asset path resolution (`asset_path`, resolved relative to `core.py`'s
  own location — both size scripts share one `assets/` folder, since
  recolouring artwork is size-independent: the same master PNG is drawn
  at whatever mm width a style requests at render time)
- Recoloured-icon temp-directory caching (`get_icon_cache_dir`,
  `cached_icon_path`, `recolour_silhouette`) — this is the fix from the
  previous round (permanent `assets/icons/` caching could serve a stale
  wrong-colour file forever; now every process run gets a fresh temp
  dir, cleaned up via `atexit`). Shared across both size scripts, so a
  "house_banner_navy.png" generated by `small.py` can be reused by
  `medium.py` if it asks for the identical master+colour, rather than
  re-running the recolour loop twice.
- `ACCENTS` / `CLEAR_VINYL_ACCENTS` / `resolve_accent`
- `ICON_ASSETS` — only the 3 generic vector-fallback entries (`floral`,
  `house`, `paw`) that are reused across multiple styles in multiple
  size scripts. A style-specific illustrated asset (e.g.
  `house_banner_master.png`, `p21_paw_trail_icon.png`) is NOT generic
  and stays defined in its own size script.
- `draw_base` / `draw_border` — **note a signature change**: `w`/`h` are
  now required keyword-only arguments (`def draw_border(c, ox, oy,
  order, weight="single", *, w, h, pad=None)`), not defaulted to a
  specific card size. This was deliberate: the original defaults
  (`w=CARD_W, h=CARD_H`) baked in one specific size, which is exactly
  wrong for a module meant to be size-agnostic. Every real call site
  already passed `w=`/`h=` as keywords, so this required no call-site
  changes (verified — see §5).
- `draw_flower_icon` / `draw_house_icon` / `draw_paw_icon` (vector
  fallback shapes) / `draw_center_flourish` (image-asset flourish)
- `fit_font_size`, `draw_curved_text`, and the two cap-height ratio
  constants (`TIMES_BOLD_CAP_HEIGHT_RATIO`, `HELVETICA_BOLD_CAP_HEIGHT_RATIO`)
- **New**: a generic grid sheet-layout (`sheet_layout`,
  `render_sheet_grid`, `render_gallery_grid`) that takes `cols`/`rows`/
  `margin_x`/`margin_y` as explicit parameters, instead of the old
  single-file version's hardcoded assumption of a 2×2 (4-up) grid. This
  is what makes Medium's genuinely different sheet shape (2-per-sheet,
  1 column × 2 rows, stacked) possible without a separate one-off layout
  function. `page_size` is also passed in explicitly by each size
  script rather than auto-derived from card orientation — Medium's card
  is wider than tall but its SHEET is portrait (stacked vertically), which
  would break a "landscape if card is wider than tall" heuristic.

**What deliberately did NOT move to core:** any per-style pixel-measured
constant, any style's own drawing function, `P02_ICON_MASTER` and
`_p02_icon_path` (P02/house_banner-specific), and the `STYLES`/
`STYLE_LABELS`/`STYLE_PRODUCT_ID`/`STYLE_CARD_SIZE` registries — all of
these are inherently tied to one specific card size or one specific
style's source artwork.

## 4. What's in each size script

Both size scripts follow the same shape:
- Import shared names from core (mostly aliased back to their old
  underscore-prefixed names, e.g. `draw_border as _draw_border`, so the
  extracted style-drawing code needed zero internal changes)
- Define their own `CARD_W`/`CARD_H`
- Define every style's drawing function + constants
- Define `STYLES` / `STYLE_LABELS` / `STYLE_CARD_SIZE` (+ `STYLE_PRODUCT_ID`
  where applicable)
- Define `draw_sticker`, `render_sheet`, `render_gallery` as thin
  wrappers around `core.render_sheet_grid`/`render_gallery_grid`,
  supplying their own grid shape and page size

**`bin_sticker_small.py`** (140×100mm): all 25 original styles, unchanged
behaviour. `render_sheet`: 2×2 grid, landscape A4 page, 14mm asymmetric
left margin (unchanged from the original).

**`bin_sticker_medium.py`** (210×140mm): 3 pilot styles only —
`p09a_borderless` (pure text, no icon), `p21_paw_trail` (raster icon +
off-centre text), `p31_olive_wreath` (raster icon-nested text). `render_sheet`:
1 column × 2 rows, **portrait** A4 page, `margin_x=0` (this card is
210mm wide — the full physical page width — confirmed via the real
borderless print test in chat; vertical margin auto-computes to 8.5mm
top/bottom, matching that same test).

## 5. Scaling methodology used for the Medium pilot styles

Medium (210×140mm) is **not** a uniform scale of Small (140×100mm) —
the aspect ratios differ slightly (1.5:1 vs 1.4:1). Every Medium
constant was derived from its Small equivalent using axis-consistent
scaling:

- **Horizontal quantities** (X positions, `MAX_WIDTH` values) × **1.5**
  (210/140)
- **Vertical quantities** (Y positions) × **1.4** (140/100)
- **Font sizes** (`MAX_SIZE`/`MIN_SIZE`) × **1.4** — treated as a
  vertical quantity, since font size fundamentally relates to cap-height
- **A raster icon's own width/height** (not its position) is scaled
  **uniformly** by ONE factor — specifically, whichever axis the icon's
  bounding box is actually constrained by (height, for both P21 and P31 —
  both icons occupy ~85–95% of the Small card's height). Stretching an
  icon's w/h independently by the two different axis ratios would visibly
  distort the artwork (circular paw pads becoming ovoid, etc.). The
  icon's *origin* (x, y) still uses normal per-axis position scaling,
  since a position isn't a shape.
- **Cutting-tolerance margins** (`P21_PAD`) are **not scaled** — these
  represent a physical cutting/lamination tolerance, not a compositional
  proportion, so the same absolute mm value applies at any card size.

**This is a first-pass derivation, not yet print-validated.** Every
Small-size constant this was derived from came from real pixel
measurements against one specific mockup image at Small's aspect ratio;
scaling preserves proportion but does not re-verify the result actually
looks right at the new size. Treat these Medium constants the same way
this project already treats a first measurement pass on any Small-size
style: print it, check it, expect to revise `*_CENTER_Y`/`*_MAX_WIDTH`/
`*_MAX_SIZE` values based on a real print test, same as Small's own
history of corrections (documented inline in `small.py`'s comments for
several styles, e.g. P21's street-width recalculation, P31's raised
size floors).

## 6. Verification already done

- **`bin_sticker_small.py` is a byte-for-byte identical extraction.**
  Rendered all 25 styles × 3 different sample orders (a standard sample,
  an edge-case long address, an edge-case short address) through both
  the original single-file `bin_sticker.py` and the new
  `core.py`+`small.py` split, and diffed the raw PDF content streams
  (not just file size — the actual drawing operators). Zero differences
  across all 75 renders. The split changed nothing about what gets
  drawn for the existing product.
- **`draw_border`'s signature change is call-site-safe.** Confirmed via
  grep that every real call site in the extracted style code passes
  `w=`/`h=` as keywords (never positionally), so making them
  keyword-only-required in core broke nothing. Also reproduced and
  fixed a real bug during this work: an earlier draft of the core
  signature put `w`/`h` positionally *before* `weight`, which collided
  with call sites passing `weight` positionally and `w=`/`h=` as
  keywords (`TypeError: got multiple values for argument 'w'`) —
  fixed by keeping `weight` positional and forcing `w`/`h` keyword-only
  instead of reordering.
- **`bin_sticker_medium.py`'s sheet layout matches the validated print
  test exactly.** Called `core.sheet_layout` directly with Medium's
  real dimensions and confirmed it outputs `margin_x=0mm`,
  `margin_y=8.5mm`, and card positions at y=148.5mm/y=8.5mm — identical
  to the numbers confirmed via the real paper print test earlier in this
  project.
- **Smoke tests passed** for both scripts: full gallery render, sheet
  render, default-style fallback (no `style` key given), and — for
  Medium specifically — the over-capacity guard (3 orders into a 1×2/
  2-slot grid correctly raises `ValueError`) and both text edge cases
  (long/short address).
- Both scripts were also confirmed to **coexist correctly in one Python
  process** (import both, render from both) — relevant since they share
  one icon cache directory via core.

## 7. What's NOT done yet — please flag if Cursor finds more

- **`test_bin_sticker.py` has not been updated for the new file
  structure.** It was written against the single-file `bin_sticker.py`
  (`import bin_sticker as bs`) and will fail to import as written, since
  `STYLES`/`draw_sticker`/etc. now live in `bin_sticker_small.py`. This
  needs a rewrite (or a parallel `test_bin_sticker_medium.py`) before
  either script has automated test coverage again.
- **Only 3 of Small's 25 styles have a Medium version.** The other 22
  haven't been scaled yet.
- **The Medium pilot styles are not print-validated** (see §5) —
  treat the current constants as a starting point for a real paper test,
  not a finished result.
- **No `assets/` folder exists anywhere in this project's uploaded
  files** (checked directly — not present in project knowledge). Every
  illustrated style (house_banner, the wreaths, duck/dog/cat families,
  p09a excluded since it has no icon) currently falls back to its plain
  vector shape in any environment without that folder, including the
  sandbox this work was verified in. This predates the split and isn't
  something the split changed, but worth knowing if Cursor's local
  checkout also lacks it, or specifically checking that it doesn't.

## 8. How to work with these files going forward

**Adding a new style to an existing size** (e.g. a 4th Medium style):
define its drawing function + constants directly in that size's script
(`small.py` or `medium.py`), using the `_asset_path`/`_draw_border`/etc.
aliases already imported at the top of that file, then add it to that
file's own `STYLES`/`STYLE_LABELS` dicts. No changes to `core.py` needed
for this.

**Porting a Small style to Medium** (or any future size): follow the
axis-consistent scaling method in §5 as a starting point, but treat the
result as provisional until print-tested — same discipline already used
throughout this project for first-pass pixel measurements.

**Adding a new size entirely** (e.g. Large, 200×287mm): create a new
`bin_sticker_<size>.py` following the same shape as `medium.py` — import
shared code from core, define `CARD_W`/`CARD_H`, define styles +
registries, and figure out the right `cols`/`rows`/`margin_x`/`margin_y`
for `core.render_sheet_grid` based on that size's actual real-world sheet
layout (don't assume 2×2 — check the real print math first, the way
Medium's 1×2 stack came from the actual validated print test rather than
being assumed).

**Changing shared behaviour** (e.g. another icon-caching fix, a font-fit
tweak): edit `bin_sticker_core.py` once — every size script picks up the
change automatically on next import. This is the main payoff of the
split: a shared bug fix no longer needs to be applied N times across N
size files.

**What a bug in one size script can and can't affect:** a bug in
`medium.py`'s style-drawing code is structurally isolated from
`small.py` — they're different files with different `STYLES` dicts, and
neither imports the other. A bug in `core.py`, however, can affect both,
since both depend on it — treat changes to `core.py` with the same care
as changes to any shared library, and ideally re-run both size scripts'
smoke tests after any core change (there's no automated test suite
covering core directly yet — see §7).
